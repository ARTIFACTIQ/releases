How We Ensure Model Quality: Automated Evaluation in CI/CD

Published February 4, 2026 | By Artifactiq ML Team

The Problem

Every ML team faces the same challenge: how do you know if a new model is actually better? Training metrics like mAP50 from the training run are useful, but they don't tell the full story. The model needs to be evaluated against real validation data with ground truth labels.

Manual evaluation creates bottlenecks. Someone has to remember to run the comparison script, interpret results, update documentation, and publish findings. Steps get skipped. Results become stale. The website shows metrics from three releases ago.

We automated the entire process.

The Pipeline

When we publish a new model release on GitHub, a workflow automatically:

1. Downloads the released model weights
↓
2. Loads validation images and ground truth labels
↓
3. Runs inference on sampled validation set
↓
4. Matches detections to ground truth using IoU
↓
5. Calculates precision, recall, F1 scores
↓
6. Commits results to repository
↓
7. Website automatically displays updated metrics

The entire process runs on GitHub Actions runners. No local machine required. No manual steps.

Ground Truth Evaluation

We store validation labels directly in the repository alongside the images. Each label file contains bounding box annotations in YOLO format:

# Format: class_id center_x center_y width height (normalized)
0 0.4521 0.3892 0.2341 0.4567
12 0.7234 0.6543 0.1234 0.2345

When the workflow runs, it loads these labels and matches model predictions against them using Intersection over Union (IoU):

IoU = Area of Overlap / Area of Union

A detection is considered a True Positive if:

  • IoU with a ground truth box exceeds 0.5 threshold
  • The ground truth box hasn't already been matched

Unmatched detections become False Positives. Unmatched ground truth boxes become False Negatives.

Metrics Calculated

MetricFormulaWhat It Measures
Precision TP / (TP + FP) Of all detections, how many were correct?
Recall TP / (TP + FN) Of all ground truth objects, how many were found?
F1 Score 2 * P * R / (P + R) Harmonic mean of precision and recall

Baseline Comparison

Raw metrics are hard to interpret without context. Is 35% precision good? It depends on the task and the alternatives.

We compare every release against Stock YOLOv11m trained on COCO. This provides a consistent baseline:

ModelPrecisionRecallF1
Artifactiq E8 35.6% 22.1% 27.3%
Stock YOLOv11m 27.0% 52.9% 35.8%
Why the difference? Artifactiq is trained on 39 apparel-specific classes. Stock YOLOv11m is trained on 80 COCO classes. Artifactiq has higher precision on its target domain but lower recall since it doesn't detect non-apparel objects that may be in the ground truth.

Implementation

The workflow is a single GitHub Actions YAML file. Key sections:

Trigger

on:
  release:
    types: [published]
  workflow_dispatch:
    inputs:
      sample_size:
        description: 'Number of validation images'
        default: '700'

Runs automatically on every release. Can also be triggered manually with configurable sample size.

Model Download

- name: Download models from release
  run: |
    TAG="${{ github.event.inputs.model_tag }}"
    if [ -z "$TAG" ]; then
      TAG=$(gh release list --limit 1 --json tagName -q '.[0].tagName')
    fi
    gh release download "$TAG" --pattern "*.pt" --dir models/

Fetches the model weights directly from the GitHub release assets.

IoU Calculation

def calculate_iou(box1, box2):
    def xywh_to_xyxy(box):
        x, y, w, h = box
        return [x - w/2, y - h/2, x + w/2, y + h/2]
    b1, b2 = xywh_to_xyxy(box1), xywh_to_xyxy(box2)
    x1, y1 = max(b1[0], b2[0]), max(b1[1], b2[1])
    x2, y2 = min(b1[2], b2[2]), min(b1[3], b2[3])
    inter = max(0, x2 - x1) * max(0, y2 - y1)
    area1 = (b1[2] - b1[0]) * (b1[3] - b1[1])
    area2 = (b2[2] - b2[0]) * (b2[3] - b2[1])
    union = area1 + area2 - inter
    return inter / union if union > 0 else 0

Auto-Commit Results

- name: Commit results
  run: |
    git config user.name "github-actions[bot]"
    git add src/data/val-comparison-results.json
    git diff --staged --quiet || git commit -m "chore: Update comparison data"
    git push

Results are committed back to the repository. The website loads this JSON file and displays current metrics.

Data in the Repository

To make this work, we store validation data directly in the repo:

releases-repo/
├── images/val/           # 700 validation images
├── data/
│   ├── val/labels/       # Ground truth label files
│   └── dataset.yaml      # Class definitions
├── src/data/
│   └── val-comparison-results.json  # Generated output
└── .github/workflows/
    └── generate-comparison.yml

This approach has tradeoffs:

ProsCons
Self-contained, reproducible Repository size increases
No external dependencies Git LFS recommended for images
Version controlled ground truth Limited to validation subset
Works on any GitHub runner Clone time increases

For our use case with 700 validation images, the repository stays manageable with Git LFS.

Website Integration

The website loads comparison results dynamically:

fetch('src/data/val-comparison-results.json')
  .then(response => response.json())
  .then(data => {
    updateMetricsDisplay(data.summary);
    updateModelInfo(data.models);
  });

When a new release triggers the workflow, the JSON updates, and the website reflects current metrics on next page load. No deployment required.

Results

Since implementing this pipeline:

  • Every release has ground truth evaluation within 5 minutes of publishing
  • Website metrics are never stale
  • We catch regressions before they reach users
  • Comparison data is versioned and auditable
View live results: The Model Comparison page shows the latest evaluation data, automatically updated on every release.
